# task-run

Vault のルートで作業する。**完了条件の承認までは、タスクの frontmatter を変えず、実行もしない**。

## 任せる範囲
- Vault の中で完結する作業だけ: 調べもの（Web の検索・閲覧による読み取り）、資料・文章の下書き、ノートの整理・要約。
- しないこと: 外部への送信・公開（メール、投稿、push、フォームの送信など）、Vault の外のファイルの変更、ノートの削除、ほかのタスクの状態の変更。これらが要るタスクは、その部分を除いた完了条件にするか、このスキルの対象外と伝える。

## 手順
1. **タスクを決める。** ユーザーの指定から `20_tasks/` と `00_inbox/` を探して読む（タイトル＝目的、完了条件・チェックリスト・経緯・成果）。曖昧なら候補を示して選んでもらう。タイトルから目的が読み取れないときは、名前の変更案を出す。
2. **具体化する。** `grilling-html` スキルの流儀と手順で、完了条件を詰める（質問の HTML は `00_inbox/` のセッションにできる）。少なくとも次を決める。
   - 成果物: 形（ノートか、既存ノートへの追記か）、置き場所（調べものは `40_research/`、資料はプロジェクトの `10_projects/<名前>/` か `50_documents/`、知識は `30_knowledge/`）、名前
   - 範囲と、やらないこと
   - 使ってよい情報源（Vault のノート、Web など）
   - 完了の判定（何がそろえば OK か）
   - 期限（`due`）
   既にタスクの「完了条件」が十分なら、grilling は確認の1ラウンドだけにしてよい。
3. **完了条件を書き、承認を得る。** 最終確認で承認された内容を、タスクの `## 完了条件` に箇条書きで書く。あわせて frontmatter を `status: in_progress`、`start`（空なら今日）、`due`（決めた値）にし、`## 経緯` に `### <今日>` と `- task-run で完了条件を決め、実行を開始。` を足す。
4. **サブエージェントで実行する。** Agent ツールを `subagent_type: general-purpose`、`run_in_background: true` で呼ぶ。プロンプトには次をすべて書く（サブエージェントはこの会話を見られない）。
   - タスクのノートのパスと、完了条件の全文
   - 任せる範囲（上の「任せる範囲」をそのまま）と、CLAUDE.md・`80_context/_rules.md` に従うこと
   - 成果物の書き方: テンプレート（`90_system/templates/`）に従い、frontmatter の `created` は今日、`project` はタスクと同じ。書いた内容の出典を残し、確かめていないことは「未確認」と書く。既存のノートは上書きしない
   - 記録のしかた: タスクの `## 経緯` の `### <今日>` の下に、行ったこと・分かったこと・判断したこと・うまくいかなかったことを箇条書きで足す。`## 成果` に成果物へのリンク `- [[ノート名]]` を足す。タスクの frontmatter は変えない
   - 最後の報告: 作成・変更したファイルの一覧、完了条件の各項目の達成状況、未解決の点
5. **完了を待つ。** バックグラウンドで動いている間は、ほかの作業をしてよい。完了の通知（Windows の通知が出る）を受けたら、報告を要約し、見るべきファイル（タスクのノートと成果物）を示して、OK か NG かを聞く。
6. **確認の結果を反映する。**
   - OK: タスクを `status: done`、`completed: <今日>` にし、`## 経緯` に `- 結果を確認して完了。` を足す。
   - NG: 差し戻しの内容を `## 経緯` に `- 差し戻し: <内容>` と足し、手順4を、差し戻しの内容を加えたプロンプトで再実行する。完了条件を変えるときは、手順2〜3からやり直す。
7. 報告: タスクの状態、成果物、次にやること（必要なら `knowledge-harvest` で知識を取り出す）。

## 注意
- サブエージェントの報告は、作業者の報告であってユーザーの承認ではない。完了の判断は、必ずユーザーの確認で行う。
- 実行中に、取り消せない操作や外部への送信が必要になったら、サブエージェントはそこで止めて報告する（プロンプトに明記する）。
